# Agency Chief of Staff 深度优化记录

本轮以 `b2b6194` 为源码基线，优化用户请求到实际成果的工作流、团队调度、完成证据与评测。后续已获用户明确授权全局安装、提交、发布和测试；本机三个受管 Skill 入口已完成备份、安装与内容/权限读回。发布目标为 `v0.3.0-rc.7`，公开状态以 GitHub Release 为准。

## 这个 Skill 应该完成什么

它承担项目负责人的工作：理解用户目标，作出必要判断，选择专业能力与执行工具，协调独立工作，整合成果，并按完成标准验收。用户应该拿到可使用的代码、研究结论、提案、创意文本或其它明确成果。

| 工作 | Root 负责的内容 | 完成依据 |
|---|---|---|
| 研究与决策 | 核对资料，比较方案，作出有依据的选择 | 来源支持结论，关键未知明确，能用于决策 |
| 软件开发与修复 | 复现问题，定位调用链，实现并集成 | 当前实现通过相关行为、回归与兼容检查 |
| 提案与创意内容 | 保留受众、事实、意象与专业语域，写出完整成稿 | 用户要求全部覆盖，内容可直接阅读或使用 |
| 图像、视频等专业制作 | 选择当前可用的领域 Skill 和工具，衔接素材与制作 | 真实产物、规格、连续性和领域质量经过检查 |
| 多阶段或跨对话项目 | 保存必要计划与当前状态，恢复上下文，协调并收口 | 工作项、当前验证和验收标准一致 |

默认路径是：明确成果与验收 → 核对事实并判断 → 完成实际工作 → 验证与修正 → 交付。用户只要讨论或只要计划时，才停在对应阶段。保存清单、另开任务、归档和知识沉淀分别按实际请求使用。

## 查到的问题与修复

| 问题及证据 | 对用户的影响 | 本轮处理 |
|---|---|---|
| 默认启动提示词预置了讨论、建清单、开新对话、归档和沉淀整套流程 | 单次明确工作也可能被扩大成管理流程 | 默认提示词改为遵循用户目标与已有授权；详细阶段保持按需 |
| `lifecycle-intents.json` 把安排团队、持续更新进度列为新执行对话意图 | 团队或进度请求可能被误当成创建新 Task 的授权 | 删除这些混淆示例，明确完整请求和授权边界优先 |
| 执行参考要求“用户要求收口时”才运行 completion | 用户已经要求完成工作，仍可能多等一次确认 | 已授权工作连续完成分析、执行、验证和收口 |
| 清单支持 Native 启动，但同对话执行只能拼接通用状态转换 | 多做准备、误走模型查询，或停在启动提示词 | 增加 `agency_task.py start`，原子进入当前对话执行；拒绝抢占已有 Session |
| Team Planner 原先忽略依赖关系计算并行 | 依赖前项的代理被提前启动，空等或重复研究 | 按 DAG 可达性判断独立性；共享前置可后续并行，交错职责按阶段拆分 |
| Review 责任字段、岗位波次及观察位前置存在错配 | 重复负责，或在成果产生前审核旧内容 | 对齐 Review 责任与 wave；Reviewer/Supervisor 等待实际负责人；发布执行保留给获授权的 Root |
| `work_completed` 不要求 verification，新事件不保存 event_type | 无验证也可标完成，恢复时难以区分失败与审核事件 | 成功工作必须带验证；新事件保存类型和产物字节摘要，旧日志仍可读取 |
| 失败恢复和幂等键没有区分工作尝试 | 重试可能复用上一轮事件与证据，无法正常继续 | 失败使工作 blocked；重试隔离旧证据，相同命令文本可在新尝试中执行 |
| 收口只核对非空证据字符串和文件存在 | 无关文件、临时编写的 PASS、验证后被改动的产物仍可通过 | 校验真实工作事件、证据引用关系与验证时文件字节；完成与归档共同使用 |
| “完整流程”模型评测主要修改 README 一行、核对措辞 | 流程测试通过，却不能证明实际开发能力 | 新增算法修复、多模块兼容的固定行为 oracle，直接执行最终实现 |

最初的 437 项测试全部通过。随后新增的 7 个证据反例在旧实现上全部失败，具体覆盖：未记录验证、未记录验收、只有 completed 字段、无关产物、验证后改动、完成后改动、目录冒充交付文件。修复后这些反例均被拒绝，并保持合法完成与事务回滚可用。

独立复审另外复现了“观察位没有等待 Root 产物”的问题。最终修复补齐 release、高风险实现、已完成/waived 前置与显式 Review 自依赖的回归，复核通过。

## 为什么保留部分现有机制

历史 Native 用例曾暴露三文件计划导致后续阶段缺资料、Skill 描述被宿主裁剪、协议示例被误判为递归等问题。本轮保留完整八文件非执行计划、显式 Canonical Packet、Native 机械绑定和安装器封存机制；通过按需进入流程减少日常负担。

Root 的默认模型请求与 Subagent 能力分层继续独立。强模型用于需要判断的工作，有界工作按实际能力需求选择；Skill 不切换当前主线程模型，也不自行写全局配置。

本轮没有大规模重写安装、Native 身份或旧收据模块。它们服务于特定证明需求；日常 Direct/Focused 工作不应运行这些流程。高风险控制保留在相关路径中。

## 实际验证

最终运行 `PYTHONDONTWRITEBYTECODE=1 bash scripts/quality_gate.sh .`：472 项单元/集成测试通过，包结构与 40 个行为 case 契约通过，临时安装的 Canonical/Legacy/Discovery bundle 和权限一致性 smoke 通过，`git diff --check` 通过。额外用 Ruby `YAML.safe_load` 检查入口与 UI metadata；系统 Skill 的通用 quick validator 因当前 Python 缺少 PyYAML 未运行成功，没有为此安装依赖。

| 隔离前向样例 | 实际产物与检查 | 结果 |
|---|---|---|
| 平均数实现修复 | 先复现整数除法问题；修复源码并补测试；独立 oracle 验证小数、负数和空输入 | 通过；样例自测 3 项通过 |
| retry-plan 旧配置兼容 | 修改实际兼容模块；经公共调用链验证 v1/v2、零值与非法输入 | 通过；样例自测 4 项通过 |
| 客户文字提案 | 依据给定资料写出《山海归途》完整 proposal.md；选择满足预算与周期的方案，覆盖 60 秒三段故事、视听、制作和验收 | 主线程逐项复核通过；仅为文字成果 |

前向执行由独立代理读取测试目录中的完整新版 Skill 后完成。主线程另外执行冻结的行为 oracle，并读取提案原文。三个样例均未创建 `.agency` 管理目录。样例证明的是相应执行路径；没有生成图片或视频，也没有客户批准。

前向样例使用冻结的 Runtime 快照；其 `SKILL.md` 与最终源码字节一致。此后调整的团队调度和 Discovery bridge 由定向回归及最终全量门禁验证，未把这三个 Direct/Focused 样例扩称为完整 Runtime 模型验证。本机诊断产物保存在 `validation/current/optimization-20260905/`，包含实际样例、oracle 读回及两个 Runtime manifest 的差异，属于忽略目录，不进入发布包。

固定 oracle 由 evaluator 持有，case 只能选择白名单 ID。它们不执行 case 自带 shell 命令、不以模型自己改过的测试充当唯一判据；检查完成必须有唯一终态证明，单纯 `sys.exit(0)` 或 `os._exit(0)` 不能冒充通过。异常和超时保留失败摘要。

## 效率与证明边界

入口由 134 行、12,737 UTF-8 字节变为 103 行、10,816 字节，入口体积减少约 15.1%。Durable 专用说明增加了同对话启动与证据用法，按需读取。进度渲染复用本次已读取的事件列表，减少一次完整日志回读。

这些是代码与样例的可观察变化。本轮没有做同一组任务的前后 token、耗时或费用对照，不能据此推算额度节省比例。

证据门检查记录一致、引用关系和文件字节；它不能判断一段自报验证文字是否真实，也不能替代领域质量审阅。当前代码/提案样例有实际产物与检查；完整 Native 新任务创建、标题与模型绑定、自然语言隐式发现、无人值守、跨宿主以及完整带专用凭据的模型评测仍属于未验证边界。

旧日志兼容读取；缺少成功验证或字节绑定的旧完成记录不满足新的当前证明门禁，本轮没有验证这类旧任务的迁移恢复。本轮未迁移或覆盖历史任务；全局安装在用户明确授权后单独完成。

## 安装态复测与发布准备

用户明确授权后，三个全局受管入口已通过仓库安装器更新，原安装已备份在 Skill 发现目录之外。安装器退出后的内容、只读权限和 37 份受保护配置校验一致；最终三个 Skill 的内容与权限再次读回一致。测试期间另观察到 `config.toml` 的校验值变化，未覆盖或回退该文件，不能把安装时的快照扩称为全程零配置变化。

使用 Codex CLI 0.153.1 启动新的 ephemeral 进程，实际读取全局安装的完整 Canonical Skill，并在隔离目录完成 Direct 与 Durable 测试。Direct 修复及 5 项测试通过；Durable 创建清单、当前对话启动、修复、6 项测试、完成与归档全部通过，active 列表为空，归档 manifest 有效。主线程又独立执行了行为 oracle，而非仅采用模型的自述。

第一次 Durable 实测虽完成目标，但创建清单时出现参数试错。本轮补上 `create --input` 的最小 JSON 和命令说明，重新安装并以新进程复测：创建参数错误消失，实际 shell 调用由该样例首次的 24 次降为 20 次。此比较仅限这两次样例，不推算普遍的 token 或费用收益。

最后一次离线全量门禁仍为 472 项通过。发布前还发现一个只给 1 秒启动窗口的超时测试不稳定；独立诊断确认增至 2 秒后，仍会在 fixture 的 5 秒停顿中超时，并验证真实 thread 行已归档，随后全量复验通过。

CLI 测试期间出现宿主模型目录刷新超时日志，但请求正常完成；本轮不把这些测试作为 live catalog 或实际模型身份鉴证。发布按 `v0.3.0-rc.7` host-scoped prerelease 处理，完整 Native 新任务、无人值守、跨宿主、专用凭据评测与旧记录迁移边界继续单独标明。
